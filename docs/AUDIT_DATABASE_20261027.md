## Transaction and lock contract

Receipt uniqueness `(actor_id, operation, operation_key)` serializes same-key requests and stores their canonical payload plus committed response. A payload mismatch fails. Source row locking serializes different payments and cancellation. Linked finance rows are locked in ID order. The original refund implementation remains owner-only as an internal helper, with role/payload-aware wrapper; concurrent refunds lock the original income row. Gift claim's existing Gift-row→code-row lock order remains unchanged.

Payment calls require a stable intent key, real amount/date/method and one currency. Multiple historical expectations fail with reconciliation required. Expected rows are reduced/cancelled; actual payments are distinct recognized movements. Refunds are compensating entries; cancellation is not evidence of cash being returned. Side-effect triggers create the existing Supabase notification outbox inside the transaction. Payment commission creation/update joins that transaction; a currency mismatch rolls the entire command back.
