## Public submission and challenge integration

`PublicChallenge.jsx` is an optional compact bilingual widget with accessible status/retry controls, bounded script loading, expiration/error invalidation and teardown. Its hook passes tokens to website booking, Fast Request, Gift Card request, booking-code redemption, Gift Card claim, review submission and referral validation. Submit handlers guard readiness and busy state; failed submissions refresh single-use tokens but retain the same business operation key. The invitation route keeps its widget mounted while validating and offers explicit retry/continue-without-attribution on dependency failure. Referral failures carry safe typed errors, not false invalid-code results.

`VITE_TURNSTILE_SITE_KEY` is public build configuration. `TURNSTILE_SECRET_KEY` is server-only. Both sides use action `public_submission`, and the server checks the request hostname. Static and Function report-only CSP permit the challenge origin. No key plus enforcement off preserves current submission behavior. Server enforcement on with no configured secret fails closed with HTTP 503; a mismatched/missing frontend site key is a release configuration error, not a usable enforcement rollout. Do not enable enforcement until compatible frontend/configuration and keyboard/mobile/provider verification pass. Synthetic provider callbacks are not proof that a real challenge was solved.

Canonical booking persistence remains authoritative. Optional notification linking must not convert an already saved request into an unsaved-request claim; loss/retry reuses the same booking operation key. The duplicate-success response is not permission to create a fresh notification ownership credential from a booking identifier.

## Finance command controls — corrective follow-up

The Finance cards previously treated only recognized **linked** transactions as immutable, although the database also forbids direct changes to recognized manual income and expenses. The narrow `financeEntryActions()` contract now offers Edit only for pending/expected rows without reversal or recognition evidence (`reversal_of`, `recognized_at`, `admin_confirmed_at`, `reversed_at`); Archive additionally requires an active draft. This is conservative UI behavior, not a substitute for the existing SQL RLS/trigger guards. Unknown, cancelled, void, reversed, reversal and recognized rows remain read-only, including archived recognized rows.

Active original confirmed income retains the existing refund flow. Expenses do not acquire an invented reversal command: the UI explains that an authorized audited correction requires review. Fully reversed entries and reversal rows are not offered another refund. Details remain available. Start-edit, save and archive handlers check the current loaded row; a successful refresh that makes an open editor ineligible clears that stale editor and reports the change. A later concurrent server change still relies on the unchanged row-version/database protection.
