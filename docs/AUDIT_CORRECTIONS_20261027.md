## P1: stale customer reminders

Confirmation-derived jobs previously compared the confirmation revision but not the current excursion schedule or eligibility. A date/time change, cancellation or disabled excursion could therefore leave the revision unchanged and allow stale inbox/push delivery while its outbox update was pending.

Creation and dispatch now share `upcomingReminderState()`. It requires a currently eligible confirmed booking, rejects cancelled/archived/completed business states, requires any linked activity to exist and remain active, and derives the exact intended reminder time from current canonical timing and the enabled rule offset. Dispatch checks that time independently before writing an inbox item or attempting push. New jobs also carry a reminder-specific revision. Existing jobs retain compatibility with their original event revision, but receive the same independent eligibility/schedule checks. Unrelated update timestamps alone do not invalidate new reminders.

Unavailable or malformed authority produces no inbox/push. Bounded backoff uses the attempt counters returned by the atomic job claim, which also rechecks due/retry timing. Exhaustion is explicit rather than an infinite retry. This is validation against a current authoritative read, not an atomic transaction across Supabase and D1; a concurrent change after that read remains a distributed-system limitation.

Behavioral reproduction before the fix: **26 passed / 10 failed**. Final expanded suite: **58 passed / 0 failed**, including new and legacy jobs, pending outbox updates, date/time changes, disabled/cancelled/missing activities, contradictory/terminal booking states, rule-offset changes, unchanged positive controls, unrelated edits, authority outage/recovery and stale retry readers. All providers are intercepted; no real notification was sent. See [notification ledger](AUDIT_NOTIFICATIONS_20261027.md).

The UI previously treated an unlinked manual entry as editable even when its recognized ledger status made the database reject Edit/Archive. `financeEntryActions()` now exposes those actions only for genuine pending/expected drafts without recognition/reversal evidence, regardless of source linkage. Click/save/archive handlers recheck the current entry; a refreshed draft that became recognized closes its stale editor rather than attempting a forbidden write.

Recognized manual income retains the existing authorized refund/reversal dialog; recognized expenses and other read-only entries show details and truthful correction guidance. No new expense-reversal command, direct ledger edit, monetary semantics or grant is introduced. Final cross-review corrected two adjacent controls under the same contract: booking source linkage is read-only with the original link preserved (fixed-excursion/leaflet draft metadata remain editable), and all refund close paths respect the in-flight guard so reopening cannot create a second intent during submission.
