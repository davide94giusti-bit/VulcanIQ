### Focused stale-reminder correction

The first executable reproduction ran before runtime edits: **26 passed / 10 failed**. Nine changed/ineligible reminder cases incorrectly wrote an inbox entry, and unavailable authority had no bounded retry counter. The unchanged eligible control passed. Subsequent coverage includes the exact legacy confirmation-derived row contract, both new and legacy changed/unchanged cases, unrelated updates, date-only bookings, replacement publication, recovery and competing-runner backoff; final total is **58 passed / 0 failed**.

- New reminders store their own source revision and canonical event type `upcoming_reminder`. The revision binds booking/activity identity, canonical date/time/timezone, preparation profile, offset and computed schedule; unrelated `updated_at` changes do not invalidate them.
- Publication and dispatch share `upcomingReminderState`. Dispatch recomputes the exact schedule without a future-only scheduling filter, but rejects an activity whose start is already past. Booking cancellation/decline/archive, cancelled/lost/completed/review-stage leads, missing linked activities, inactive activities, and cancelled activities cannot receive an upcoming reminder. Legitimate unlinked/date-only bookings retain the existing 09:00 UTC fallback.
- Legacy jobs retain the original event revision check and additionally require current eligibility plus exact `scheduled_for` equality. Unchanged eligible legacy jobs are not blanket-cancelled; stale ones are cancelled before creating an event/inbox or sending push, even if the relevant outbox event remains pending. No historical rows are rewritten during release.
- Missing records are ineligible; HTTP/configuration/JSON-shape failures remain unavailable authority and send nothing. The existing job attempt fields provide exponential backoff (60s,120s with the default three-attempt limit), then terminal `canonical_validation_exhausted`. Recovery during that window can still deliver once. Atomic job claims recheck due/backoff times and return current attempt/max counters; stale readers cannot bypass another runner's backoff.
- No new dependency, schema, migration, scheduling activation, real-provider send or remote change is required/performed by this correction. Existing confirmation, cancellation, reschedule, ownership, delivery-lease and privacy-safe preparation flows remain in place.
